# Purpose

Checks `checkDailyLossKillSwitch(unitName)` in
`magi-core/lib/daily-loss.js`. Two independent layers (Jun-approved dual
protection, 2026-10-08, magi-core#581):

* **unit**: the unit's realized P&L for the current Eastern Time day vs
  `-DAILY_LOSS_LIMIT_USD`;
* **account**: the whole account's daily realized P&L vs
  `-ACCOUNT_DAILY_LOSS_LIMIT_USD` (defaults to the unit limit when unset).

# Behaviour

At or beyond EITHER limit, risk-increasing orders are blocked for the rest
of the trading day with `blocked_by: 'daily_loss_kill_switch'`. The result
reports `scope: 'unit' | 'account'` and echoes `realized_pnl_usd`,
`limit_usd`, `accountPnlUsd`, `accountLimitUsd`. Risk-reducing orders still
pass so exposure can always be unwound. A position-lookup failure fails
closed and treats the order as risk-increasing. `notifyKillSwitchOnce()`
alerts once per unit/scope per ET day.

Notes on the current implementation (`magi-core`, verified 2026-10-08):

* Unit attribution follows the evaluator's FIFO rule — a close belongs to
  the earliest non-terminal entry for the symbol/direction; orphan closes
  fall back to the executing unit so losses are never silently dropped.
* Realized P&L comes from `AUTO_CLOSE` rows' `pnl_amount`, which is gross
  of fees — realized losses are slightly understated (reported drift).
* Each layer fails open independently on a BigQuery lookup error (a warning
  is logged); non-finite values never trip.
* Daily boundary is the ET calendar day (`etDateString`,
  `America/New_York`).
* 60s in-process cache per unit and for the account figure.
* Account daily **valuation** loss (MTM change adjusted for flows) is a
  separate metric used by the experiment gates, not by this switch — the
  two are never summed.

# Constitution basis

[POSITION MANAGEMENT](/system/constitution/position-management.md): daily
