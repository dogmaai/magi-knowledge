# Purpose

Checks `checkDailyLossKillSwitch(unitName)` in
`magi-core/lib/daily-loss.js`. Two independent layers (Jun-approved dual
protection, 2026-10-08, magi-core#581):

* **unit**: the unit's realized P&L for the current Eastern Time day vs
  `-DAILY_LOSS_LIMIT_USD`;
* **account**: the whole account's daily realized P&L vs
  `-ACCOUNT_DAILY_LOSS_LIMIT_USD` (defaults to the unit limit when unset).

# Behaviour

At or beyond EITHER limit, risk-increasing orders are blocked for the rest
of the trading day with `blocked_by: 'daily_loss_kill_switch'`. The result
reports `scope: 'unit' | 'account'` and echoes `realized_pnl_usd`,
`limit_usd`, `accountPnlUsd`, `accountLimitUsd`. Risk-reducing orders still
pass so exposure can always be unwound. A position-lookup failure fails
closed and treats the order as risk-increasing. `notifyKillSwitchOnce()`
alerts once per unit/scope per ET day.

Notes on the current implementation (`magi-core`, code-inspected
2026-10-08). The amendments since the 2026-10-09 `verified` stamp — the
2026-10-08 dual-layer update and the 2026-10-19 additions (the `CLOSE`-row
aggregation, the owner-predicate widening, and the order-time
classification lag note) — were re-verified by Jun on 2026-10-20
(`stable` restored):

* Unit attribution follows the evaluator's FIFO rule — a close belongs to
  the earliest entry for the symbol/direction that was still open at close
  time: open rows (result NULL/HOLD), or WIN/LOSE entries whose
  `exit_timestamp` is at/after the close (magi-core#627). Orphan closes
  fall back to the executing unit so losses are never silently dropped.
  When one close spans entries owned by multiple units the whole amount
  still lands on the single earliest owner — the same approximation
  AUTO_CLOSE has always used; proportional attribution per covered entry
  is tracked as magi-core#628.
* Realized P&L comes from close-event rows' `pnl_amount`: `AUTO_CLOSE`
  (guard-triggered) and `CLOSE` (unit-initiated discretionary sell, added
  2026-10-19 — see [trades: Close events](/system/echidna-tables/trades.md)).
  `ORPHAN_CLOSE` rows carry no attributable basis and are review items,
  not P&L. **Resolved drift**: `lib/daily-loss.js` originally filtered
  `result = 'AUTO_CLOSE'` only — magi-core#627 extended both queries to
  `AUTO_CLOSE` + `CLOSE`. **Classification lag — resolved 2026-10-19**:
  the evaluator only selects rows
  ≥24h old and runs once daily, so a discretionary sell's `CLOSE`
  classification lands up to ~2 days after its fill and its realized
  loss is invisible to this switch for that ET day. magi-core#630
  removed the lag by writing `CLOSE`/`pnl_amount` at order time (magi-core
  #632, merged 2026-10-19); `AUTO_CLOSE` already lands same-day.
  Values are gross of fees, so realized losses are slightly understated
  and the trip can fire later than a net-of-fees accounting would
  (reported drift).
* Each layer fails open independently on a BigQuery lookup error (a warning
  is logged); non-finite values never trip. Fail-open on lookup failure is
  the implemented behaviour — whether it should instead fail closed is
  flagged to Jun as an open question, not silently decided here.
* Daily boundary is the ET calendar day (`etDateString`,
  `America/New_York`).
* 60s in-process cache per unit and for the account figure.
* Account daily **valuation** loss (MTM change adjusted for flows) is a
  separate metric used by the experiment gates, not by this switch — the
  two are never summed.
