# Purpose

Hard position-sizing limits, checked against live broker account/positions
(MooMoo) **plus exposure already committed but not yet a position** (see
[In-flight reservation](#in-flight-reservation-magi-core729-item-4)):

* **Max concurrent positions** — `MAX_CONCURRENT_POSITIONS`. New opens blocked
  when at the limit (`blocked_by: 'position_limit_layer'`).
* **Max per-position exposure** — `MAX_POSITION_PCT` (0.15) of equity,
  multiplied by the current VIX regime's position multiplier
  (defaults `CALM`/`LOW_FEAR` 1.0, `HIGH_FEAR` 0.7, `EXTREME_FEAR`/`PANIC`
  0.3 — `POSITION_MULTIPLIER_BY_LEVEL` in `magi-core/lib/vix.js`, overridable
  per level by a `POSITION_MULTIPLIER` row in
  [optuna-params](/system/echidna-tables/optuna-params.md) — **except
  `EXTREME_FEAR`, which is locked at 0.3 during the L6 policy validation
  period**, Jun 2026-10-12), so the default effective cap is
  15% / 10.5% / 4.5% of equity. The multiplier scales the cap only — it is
  never also applied to the order quantity. Under the new L6 policy
  (`L6_POLICY=live`, see [L6](l6.md)) an `EXTREME_FEAR` order that exceeds
  the cap is **clamped to the allowed qty** for any order kind — a
  zero-headroom order is skipped; existing positions over the cap are
  never force-liquidated by this layer. Oversized orders are blocked and a
  `max_qty` is returned (`blocked_by: 'position_size_layer'`). A boosted
  (L2.6 confidence-band) order whose boost alone exceeds the cap is clamped
  back to `max_qty` instead and journaled as a `WARN_ONLY` row.

Both limits apply to orders that increase exposure on either side (BUY adding
long, SELL opening/adding short); orders that reduce or close a position pass
so risk can always be unwound. The concurrent-position count is the live
broker account, shared by every unit trading that account, **plus symbols
with an in-flight order that the broker position list does not show yet**
(since magi-core#731; with `L15_RESERVATION=off` it is the broker positions
alone, as before).

# Behaviour

The check is fail-safe: if the live broker lookups (account, positions, quote)
error, it logs and is non-blocking (does not falsely block on infrastructure
hiccups). Errors in the guard's own evaluation propagate (fail closed). When no
VIX regime is cached the multiplier defaults to 1.0. The reservation lookups
below are non-blocking in the same way: a failed working-order,
`order_intents` or Firestore read means that source counts nothing.

# In-flight reservation (magi-core#729 item 4)

Several unit sessions trade one shared broker account. Broker positions show
only **filled** shares, so two sessions could both pass L1.5 on the same
snapshot before either order appears. Since magi-core#731 two layers narrow
that window. They lower the probability of an overshoot; they do not make
L1.5 atomic. All of this applies only to orders that increase exposure, and
reservations are only ever added in the order's own direction — they never
loosen a cap.

**Layer 1 — at L1.5 time.** Committed-but-unfilled exposure counts against
both caps (a held-position count that includes in-flight symbols, and the
per-symbol exposure cap with in-flight shares added to the existing
position):

* the unfilled remainder (`qty − filled_qty`) of broker orders still working
  (order history, status not terminal);
* plus one of two second sources, by backend:
  * **Option A (default)** — `order_intents` rows whose latest event is
    `PENDING` and whose `PENDING` was journaled within the last 2 minutes
    (the broker POST is in flight). Intents are read from the last 15
    minutes; a row with no `PENDING` in that window is ignored.
  * **Option B (opt-in)** — live reservations from Firestore (below), which
    replace the `order_intents` estimate. A working broker order already
    linked to a reservation by broker order id is counted once.

**Layer 2 — immediately before the broker POST.**

* Option A: after this order's own `PENDING` intent is journaled, intents
  journaled **after this order's L1.5 broker snapshot and before its own
  intent** (ties by `intent_id`) are added and the caps re-checked. Dead
  intents (`REJECTED`, `LOST`) and anything layer 1 already counted are
  skipped (a working order layer 1 counted is netted off, so only the part
  that filled since is added). Of two racing orders the first-journaled wins;
  the later one is refused: its intent is closed `REJECTED` with
  `detail = 'L1.5 reservation: …'`, nothing reaches the broker, and the
  caller gets `blocked_by` `position_limit_layer` / `position_size_layer`.
  A failed intent lookup is non-blocking; a throwing check fails closed.
* Option B: a Firestore transaction checks the caps against the caller's
  snapshot plus every other live reservation and records this order's
  reservation atomically, after every other guard and before the POST. A
  refusal is final. A store or RPC failure is non-blocking (the order
  proceeds unreserved).

**Option B reservation store.** One document per account
(`{collection}/{accountKey}`, default collection `l15-reservations`,
account key `moomoo-<TRD_ENV>` so SIMULATE and REAL never share), holding
`active[reservationId]`. Lifecycle after the broker answers:

| Broker answer | Reservation |
|---|---|
| Not sent / refused before the POST | Released. |
| Response lost / unknown disposition | Kept until TTL (the order may be live). |
| Accepted, still working or partially filled | Kept, linked to the broker order id with the largest cumulative fill seen. |
| Final: `FILLED_ALL` | Marked filled at the requested quantity (or more, if a larger quantity was reported). Not dropped. |
| Final: terminal status with a positive reported quantity | Marked filled at the larger of that quantity and any earlier observation. |
| Final: terminal status, quantity unreported or contradicted (e.g. a `0` after fills were seen, or `0` beside `CANCELLED_PART`) | Marked filled at the **requested** quantity, at least what was seen — an upper bound, never read as 0. |
| Final: no-fill terminal status with an **explicit** `0` and nothing seen before | Released. |

A filled reservation is kept so a session whose broker snapshot does not
show the fill yet still counts it; it stops counting once a snapshot was
taken at least `FILL_REFLECTION_MARGIN_MS` (**5 000 ms**, a code constant —
**an unmeasured assumption**, deliberately biased to over-count for a few
seconds rather than let a cap be exceeded) after the fill was recorded.
Each reservation counts only what a snapshot cannot show yet: an open order
counts its quantity minus the reflected fills; a final order counts its
actual final fill until reflected. Reservations expire after a TTL
(default 10 minutes; for a filled one it runs from the fill), so a crashed
dispatcher's reservation lapses instead of needing fencing.

| Setting | Default | Meaning |
|---|---|---|
| `L15_RESERVATION` | on | `off` disables both layers and both backends. |
| `L15_RESERVATION_BACKEND` | unset (option A) | `firestore` selects option B. |
| `L15_ACCOUNT_KEY` | `moomoo-<TRD_ENV>` | Reservation document id. |
| `L15_FIRESTORE_PROJECT` / `_DATABASE` / `_COLLECTION` | `screen-share-459802` / `arc-sig-experiment` / `l15-reservations` | Firestore location. |
| `L15_RESERVATION_TTL_MS` | 600000 | Reservation lifetime. |

Provisioning the Firestore database and the unit service accounts' IAM, and
setting the flags, are Jun's operations. As of magi-core `63888b2`
`deploy.yml` sets none of the `L15_*` variables, so the code default
(option A) is what a deployment of that revision runs; live Cloud Run
configuration was not inspected.
